# Coding agent с tool calling (ДЗ № 1)

Консольный агент получает задачу на изменение небольшого проекта, сам выбирает инструменты,
читает и меняет файлы, запускает тесты и решает, когда закончить работу. Модель только
**предлагает** действия. Решение принимает runtime: схема → policy → режим → бюджет → журнал → исполнение.

Реализованы все уровни задания, до 10 баллов:

| Уровень | Что сделано | Где в коде |
|---|---|---|
| Блок 1 | agent loop, несколько tool calls в одном ответе, ошибки инструментов, `Bash` с таймаутом и лимитом вывода | `agent/runtime.py`, `agent/tools.py` |
| Блок 2 | policy-файл (команды и директории allow/deny), режимы `safe`/`auto`, подтверждения со стоп-и-продолжить | `agent/policy.py`, `policy.json` |
| Блок 3 | `run_id`, состояние на диске, «началось/завершилось», неопределённые вызовы, повтор `tool_call_id` | `agent/runtime.py`, `agent/store.py`, `agent/faults.py` |
| Блок 4 | Plan Mode: структурированный план, утверждение и отклонение | `agent/plan.py`, `agent/runtime.py` |
| 8 баллов | единый бюджет: запросы к модели, tool calls, побочные эффекты, байты результатов | `agent/budget.py` |
| 9 баллов | шаги плана становятся задачами с зависимостями; результат задачи проверяет runtime | `agent/plan.py` |
| 10 баллов | журнал изменений со снимками и хешами, diff, безопасный откат по `run_id` | `agent/journal.py` |

Агент написан на Python 3.10+ и использует только стандартную библиотеку, без агентских фреймворков.
HTTP-клиент к OpenAI-compatible Chat Completions API (`agent/llm.py`) написан на `urllib`.

## Установка

Нужны Python ≥ 3.10 и Bash (macOS/Linux; на Windows — WSL).

```bash
git clone <URL этого репозитория> && cd <папка>
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt        # внешних зависимостей нет; pytest — по желанию: requirements-dev.txt
```

`.env` подхватывается автоматически, если запускать команды из корня проекта; уже заданные переменные окружения он не перезаписывает.

## Инструменты

| Инструмент | Аргументы | Класс | Plan Mode | `safe` | `auto` | Повтор после сбоя |
|---|---|---|---|---|---|---|
| `Bash` | `command`, `cwd` | exec | запрещён | подтверждение | сразу | **нет** |
| `list_files` | `path` | read | да | сразу | сразу | да (без побочных эффектов) |
| `read_file` | `path` | read | да | сразу | сразу | да (без побочных эффектов) |
| `write_file` | `path`, `content` | write | запрещён | подтверждение | сразу | да (идемпотентен) |
| `delete_file` | `path` | delete | запрещён | подтверждение | подтверждение | да (идемпотентен) |
| `submit_plan` | структура плана | control | только здесь | сразу | сразу | — |
| `complete_task` | `task_id`, `summary` | control | нет | сразу | сразу | — |

Каждый инструмент передаётся модели с именем, описанием и JSON Schema аргументов (`ToolSpec.to_openai()`).
Результат возвращается сообщением `role: tool` с исходным `tool_call_id`. Ошибка инструмента не роняет процесс:
модель получает `{"ok": false, "error": "...", "message": "..."}` и выбирает следующий шаг.

**Почему так решено с повтором.** `write_file` пишет полный content, поэтому повтор даёт то же итоговое состояние.
`delete_file` при отсутствующем файле отвечает «уже нет», и итог тоже одинаковый. Чтение побочных эффектов не имеет.
`Bash` не повторяется: произвольная команда может быть неидемпотентной (дописать в файл, сходить в сеть).

## Запуск агента

```bash
# Plan Mode + safe (по умолчанию)
python3 -m agent run "Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй. Сам найди нужные файлы, внеси исправление и запусти тесты."

# без плана, auto-режим
python3 -m agent run "…" --mode auto --no-plan

# подтверждать прямо в консоли (состояние всё равно сохраняется перед вопросом)
python3 -m agent run "…" -i

# детерминированное демо без LLM
python3 -m agent run "Исправь расчёт" --mode auto --no-plan --scripted demo/scripted_no_plan.json
python3 -m agent run "Исправь расчёт" --scripted demo/scripted_plan.json
```

Команда печатает `run_id`. Все остальные команды работают с ним:

| Команда | Что делает |
|---|---|
| `python3 -m agent status <run_id>` | статус, ожидаемое решение, бюджет, чеклист задач |
| `python3 -m agent list` | все запуски |
| `python3 -m agent calls <run_id>` | журнал tool calls (фаза, задача, статус, попытки) |
| `python3 -m agent approve <run_id>` / `deny <run_id> --reason "…"` | подтверждение или отказ для ожидающего действия |
| `python3 -m agent plan show\|approve\|reject <run_id>` | Plan Mode |
| `python3 -m agent resume <run_id>` | продолжить после сбоя или прерывания |
| `python3 -m agent recover <run_id> --action retry\|fail\|abort [--changes attribute\|external]` | решение по неопределённому вызову или конфликту |
| `python3 -m agent tasks <run_id>` | задачи и подтверждения их результата |
| `python3 -m agent diff <run_id> [--entries]` | изменения файлов запуска |
| `python3 -m agent rollback <run_id>` | откат изменений запуска |
| `python3 -m agent abort <run_id>` | завершить запуск |
| `python3 -m agent policy-check <tool> '<json>' [--mode auto] [--phase planning]` | решение policy для одного вызова без модели |

Другой policy-файл: `--policy path/to/policy.json` или переменная `AGENT_POLICY`.

## Policy

`policy.json` лежит вне `workspace`, и агент не может его изменить: все пути агента ограничены workspace,
а сам файл и `.agent_runs/` дополнительно помечены как защищённые. Policy перечитывается **перед каждым исполнением**,
поэтому изменение policy во время ожидания подтверждения применяется сразу.

```json
{
  "workspace": "workspace",
  "runs_dir": ".agent_runs",
  "commands": {
    "allow": ["python3 -m unittest -v", "python3 -m unittest", "python3 -m unittest test_order -v", "ls", "ls -la", "pwd"],
    "deny":  ["rm", "sudo", "curl", "wget", "git push", "bash -c", "sh -c", "python3 -c", "pip install"]
  },
  "directories": {
    "allow": ["workspace"],
    "deny":  ["workspace/private", "workspace/.git"]
  },
  "bash":    {"timeout_sec": 30, "max_output_bytes": 20000},
  "files":   {"max_read_bytes": 100000, "max_write_bytes": 200000},
  "journal": {"exclude": ["__pycache__", "*.pyc", ".pytest_cache", ".DS_Store"]},
  "budget":  {"model_calls": 40, "tool_calls": 80, "side_effects": 20, "result_bytes": 300000}
}
```

Правила (`agent/policy.py`):

* **Команды.** `commands.allow` — точные строки. Команда разрешена, только если её токены в точности совпадают с одной из них.
  `commands.deny` — последовательности токенов: команда запрещена, если содержит такую последовательность где угодно.
  Например, `rm` запрещает `rm -rf x`, а `bash -c` запрещает `env bash -c …`. Запрет сильнее разрешения,
  всё неразрешённое запрещено. Любой Bash-синтаксис отклоняется целиком: `| & ; < > ( ) $ \` \ " ' * ? [ ] { } ~ ! # % ^`,
  переводы строк и `VAR=value cmd`. Поэтому конвейеры, подстановки, перенаправления и `bash -c '…'` не проходят.
  В allowlist нельзя записать команду с таким синтаксисом: policy не загрузится.
* **Аргументы-пути** в команде (содержат `/`, `..` или абсолютные) проверяются по тем же правилам, что и пути файловых инструментов.
* **Директории.** Все значения канонизируются через `realpath`. `directories.allow` обязаны лежать внутри workspace, иначе policy не загрузится.
  Путь разрешён, если он внутри allow и не внутри deny; deny проверяется первым.
* **Пути агента.** Только относительные. `..` и абсолютные пути отклоняются. Если `realpath` отличается от лексического пути,
  значит путь проходит через симлинк, и он отклоняется (даже если симлинк ведёт внутрь workspace). Файлы открываются с `O_NOFOLLOW`.
* **Рабочая директория `Bash`** проверяется так же, как путь: разрешённая команда в запрещённой директории отклоняется.
* **Окружение `Bash`** минимальное (`PATH`, `HOME`, `LANG`, `PYTHONDONTWRITEBYTECODE=1`): секреты агента вроде `OPENAI_API_KEY` в процесс не попадают.
  Процесс запускается в отдельной группе и при таймауте убивается целиком. Вывод ограничен и помечается `truncated`.

> Policy и проверка команд не заменяют изоляцию: программа, запущенная через `Bash`, работает с правами пользователя.
> Используйте учебную копию проекта без секретов.

Проверить решение policy без модели можно так:

```bash
python3 -m agent policy-check Bash '{"command": "python3 -m unittest -v", "cwd": "."}'
python3 -m agent policy-check Bash '{"command": "python3 -m unittest -v | cat", "cwd": "."}'
python3 -m agent policy-check Bash '{"command": "ls", "cwd": "private"}'
python3 -m agent policy-check read_file '{"path": "../policy.json"}'
python3 -m agent policy-check delete_file '{"path": "order.py"}' --mode auto
```

### Режимы

* **safe** — чтение сразу; `write_file` и `Bash` после подтверждения; удаление после подтверждения.
* **auto** — чтение сразу; `write_file` и `Bash` сразу, если прошли policy; удаление после подтверждения.

Когда нужно подтверждение, runtime сохраняет состояние, печатает действие (для `write_file` — diff предлагаемого изменения)
и останавливается. Дальше пользователь отвечает:

```bash
python3 -m agent approve <run_id>
python3 -m agent deny <run_id> --reason "не трогай этот файл"
```

Запуск продолжается тем же `run_id`. После отказа модель получает результат
`{"error": "denied_by_user", "reason": "…"}` и может изменить свои действия.

## Plan Mode и утверждение плана

`run` по умолчанию начинается в фазе **planning**. В ней модели доступны только `list_files`, `read_file` и `submit_plan`.
Если модель всё же вызовет `write_file`, `delete_file` или `Bash`, runtime отклонит вызов с ошибкой `not_allowed_in_phase`.
Это проверяется по фазе каждого вызова, а не только по списку инструментов, показанному модели.

План — структурированные данные (схема `PLAN_SCHEMA` в `agent/plan.py`):

```json
{
  "goal": "…",
  "steps": [
    {"id": "T1", "description": "…", "depends_on": [], "tools": ["read_file"],
     "checks": [{"type": "file_read", "path": "order.py"}]},
    {"id": "T2", "description": "…", "depends_on": ["T1"], "tools": ["write_file"],
     "checks": [{"type": "file_changed", "path": "order.py"}, {"type": "file_unchanged", "path": "test_order.py"}]},
    {"id": "T3", "description": "…", "depends_on": ["T2"], "tools": ["Bash"],
     "checks": [{"type": "command_succeeded", "command": "python3 -m unittest -v"}]}
  ],
  "risks": ["…"], "assumptions": ["…"], "done_criteria": "…"
}
```

Перед тем как показать план пользователю, runtime его проверяет: схема, уникальные id, существующие зависимости без циклов,
известные инструменты, выполнимые проверки (пути проходят policy, команды есть в allowlist).
План сохраняется в `state.json` запуска, история версий — в `plan_history`.

```bash
python3 -m agent plan show <run_id>
python3 -m agent plan approve <run_id>
python3 -m agent plan reject <run_id> --reason "добавь проверку, что тесты не изменены"
```

После отклонения модель получает причину и присылает новую версию плана. Утверждение плана **не** разрешает действия заранее:
в `safe` каждая запись и каждый `Bash` по-прежнему требуют подтверждения, в `auto` действуют правила базовой части.

## Задачи (уровень 9)

После утверждения каждый шаг становится задачей: `id`, описание, зависимости, состояние (`pending → in_progress → done`)
и проверяемый результат (`checks`). Runtime запускает задачи последовательно и берёт следующей только ту,
все зависимости которой уже `done`. Порядок шагов в плане роли не играет. Каждый tool call фазы исполнения
получает `task_id` текущей задачи. Вызовы фазы планирования хранятся отдельно (`planning_calls`) и без `task_id`.

Слов модели недостаточно, чтобы закрыть задачу. Модель вызывает `complete_task`, а runtime **сам** проверяет `checks`
по фактическим данным:

| Проверка | Чем подтверждает runtime |
|---|---|
| `file_read` | в журнале вызовов этой задачи есть успешный `read_file` этого пути |
| `file_changed` / `file_unchanged` | sha256 файла сейчас против базового снимка запуска |
| `file_contains` | содержимое файла |
| `command_succeeded` | `Bash` с этой командой в рамках задачи, `exit_code == 0`, и после него дерево файлов не менялось (хеш снимка) |

Подтверждение (`evidence`: id вызова, хеши, код выхода) сохраняется в задаче. Задачи выводятся в stdout в виде чеклиста:

```
Tasks:
- [x] T1: Перечитать order.py и выяснить ожидаемое поведение
- [ ] T2: Исправить order.py  (depends on T1; in progress)
- [ ] T3: Запустить тесты  (depends on T2)
```

Состояние задач и подтверждения:

```bash
python3 -m agent tasks <run_id>
python3 -m agent status <run_id>
```

После `resume` завершённые задачи не запускаются заново: их состояние хранится в `state.json`.

## Восстановление по run_id (блок 3)

Всё состояние запуска лежит в `.agent_runs/<run_id>/state.json`: история сообщений, tool calls с аргументами,
статусами, попытками и результатами, решения пользователя, план, задачи, бюджет, журнал. Файл пишется атомарно
(tmp + fsync + `os.replace`). Запуск защищён блокировкой `flock`: после падения процесса ОС снимает её сама.

Протокол каждого действия:

1. *(одна атомарная запись)* списание бюджета + статус вызова `started` + ссылка на снимок дерева «до»;
2. исполнение инструмента;
3. *(одна атомарная запись)* результат + diff и хеши в журнале + расход `result_bytes`.

Если процесс упал между 1 и 3, после перезапуска вызов становится **неопределённым** (`uncertain`) и молча не повторяется.
Runtime сверяет дерево со снимком «до», показывает обнаруженные изменения и ждёт решения:

```bash
python3 -m agent resume <run_id>
python3 -m agent recover <run_id> --action retry  --changes attribute   # повторить (новая попытка того же tool call)
python3 -m agent recover <run_id> --action fail   --changes external    # считать шаг неуспешным и продолжить
python3 -m agent recover <run_id> --action abort                        # завершить запуск с ошибкой
```

* `retry` разрешён только для повторяемых инструментов (см. таблицу выше). Это новая попытка `attempts[n+1]` с тем же `tool_call_id`.
* `--changes attribute` относит обнаруженные изменения к запуску: они попадут в журнал и откат. `--changes external` считает их посторонними.
  Если изменения есть, этот флаг обязателен.
* Неопределённое чтение повторяется автоматически: у него нет побочных эффектов.

**Повтор `tool_call_id`.** Если модель присылает id, который уже был, с тем же именем и аргументами, runtime возвращает
сохранённый результат с пометкой `replayed` и **не** исполняет вызов ещё раз. Если имя или аргументы отличаются,
возвращается ошибка протокола `protocol_error`, и вызов не исполняется. Если сервер не прислал id, runtime назначает синтетический.

Имитация сбоя — настоящая остановка процесса через `os._exit(137)`:

```bash
python3 -m agent run "Исправь расчёт" --mode auto --no-plan --scripted demo/scripted_no_plan.json \
        --crash-at after_tool_execute:write_file
python3 -m agent status <run_id>       # «процесс прервался во время вызова …»
python3 -m agent resume <run_id>       # покажет неопределённый вызов и diff
python3 -m agent recover <run_id> --action retry --changes attribute
```

Точки отказа: `after_model_charge`, `after_tool_start`, `after_tool_execute` (между выполнением и сохранением результата), `after_result_save`.

## Бюджет (уровень 8)

Лимиты задаются в `policy.json → budget` и фиксируются в запуске при его создании. Переопределить: `run … --budget model_calls=10,tool_calls=20`.

| Счётчик | Когда списывается |
|---|---|
| `model_calls` | перед запросом к модели, запись на диск до отправки |
| `tool_calls` | при приёме ответа модели — сразу на всю пачку; ещё 1 за каждую повторную попытку |
| `side_effects` | при старте `write_file` / `delete_file` / `Bash`, атомарно со статусом `started` |
| `result_bytes` | байты UTF-8 строки результата, которую увидит модель; атомарно с результатом |

* Счётчики живут в `state.json`. `resume`, утверждение плана и повтор после сбоя их не обнуляют. Если процесс упал после списания, бюджет не возвращается.
* **Пачка — всё или ничего.** Если на все tool calls ответа (или на все побочные эффекты пачки) не хватает остатка, ни один вызов не исполняется.
* **Неизвестный размер результата.** Инструмент получает доступный остаток `result_bytes`: Bash не собирает больше, чтение файла обрезается.
  Затем runtime подгоняет итоговый результат под остаток и помечает его `"truncated": true, "truncated_reason": "result_bytes budget"`.
  Если остаток меньше 256 байт, действие не начинается.
* Исчерпан `model_calls` — запуск завершается со статусом `failed` (`budget_exhausted`).

## Журнал изменений и откат (уровень 10)

Снимок дерева — это `{путь: sha256}` всех файлов зоны агента. Содержимое хранится в `blobs/<sha256>`.
Список путей фиксирует не только изменения, но и создание и удаление файлов.

Перед каждым `write_file` / `delete_file` / `Bash`:
1. текущее дерево сверяется с последним известным состоянием. Если оно отличается, действие **не выполняется**,
   запуск ждёт решения о **конфликте** (`recover --action retry|fail|abort --changes external`);
2. сохраняется снимок «до».

После действия сохраняются снимок «после», фактический diff и хеши. `Bash` обрабатывается так же,
поэтому изменения файлов от команды тоже попадают в журнал. Для каждого затронутого файла хранятся `before`
(до первого изменения этим запуском) и `after` (после последнего).

Генерируемые файлы исключены явно: `journal.exclude` в policy (`__pycache__`, `*.pyc`, `.pytest_cache`, `.DS_Store`).
Policy не загрузится, если шаблон скрывает `*.py`, то есть исходники или тесты. Кроме того, `Bash` запускается с `PYTHONDONTWRITEBYTECODE=1`.

```bash
python3 -m agent diff <run_id>             # по файлам: before -> after, текущий хеш, «изменён извне», unified diff
python3 -m agent diff <run_id> --entries   # плюс diff каждого действия
python3 -m agent rollback <run_id>
```

Откат:
* восстанавливает **только** файлы, изменённые этим запуском: изменённые — к `before`, созданные удаляет, удалённые возвращает;
* перед записью заново проверяет policy и пути и сверяет текущий sha256 каждого файла с `after`;
* если хоть один файл изменён извне — сообщает **конфликт и не пишет ни одного файла**;
* сначала готовит все tmp-файлы, затем подменяет их через `os.replace`;
* работает после `resume` и в другом процессе;
* не выполняется, пока есть неопределённый после сбоя вызов: сначала `resume`/`recover` и явное решение `--changes attribute|external`.

## Сценарий демонстрации для защиты

```bash
# 1. Контрольная задача с планом и задачами (настоящая модель из .env)
python3 -m agent run "Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй. Сам найди нужные файлы, внеси исправление и запусти тесты." -i
python3 -m agent tasks <run_id>
python3 -m agent diff <run_id>
python3 -m agent rollback <run_id>

# 2. То же детерминированно, если модель недоступна
python3 -m agent run "Исправь расчёт" --scripted demo/scripted_plan.json -i

# 3. Сбой и восстановление
python3 -m agent run "Исправь расчёт" --mode auto --no-plan --scripted demo/scripted_no_plan.json --crash-at after_tool_execute:write_file
python3 -m agent resume <run_id>
python3 -m agent recover <run_id> --action retry --changes attribute

# 4. Пограничные случаи policy
python3 -m agent policy-check Bash '{"command": "python3 -m unittest -v; rm -rf /", "cwd": "."}'
```

Где что происходит (для вопросов на защите):

* **Почему модель выбрала инструмент** — она видит описания и JSON Schema инструментов, системный промпт со списком разрешённых команд и результаты предыдущих вызовов. Решение исполнять или нет принимает runtime.
* **Где проверяется policy** — `AgentRuntime._process_call` → `PolicyEngine.check_call` (`agent/policy.py`), заново перед каждым исполнением, в том числе после подтверждения и при повторе.
* **Что происходит при отказе** — вызов получает статус `denied` или `rejected`, модель получает `role: tool` с причиной и продолжает.
* **Исчерпание бюджета** — `Budget.shortfall` до начала действия; пачка целиком; запуск `failed` при исчерпании `model_calls`.
* **Сбой** — `AgentRuntime._reconcile`: `started` без результата превращается в `uncertain`, дальше решение пользователя (`recover`).
* **Подтверждение результата задачи** — `verify_task` в `agent/plan.py` сверяет журнал вызовов, хеши и содержимое файлов.
* **Откат** — `Journal.rollback` в `agent/journal.py`: policy → хеши → staging → `os.replace`.

## Ограничения

* Проверка команд — точные строки без shell-синтаксиса. Это осознанное упрощение по условию задания, не песочница.
* Блокировка запуска использует `fcntl` (macOS/Linux/WSL).
* Задачи выполняются последовательно (параллельность не требуется).
